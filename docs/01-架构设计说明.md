# 架构设计说明

项目：FusionRAG —— 图增强检索生成（GraphRAG）企业知识库问答系统

---

## 1. 总体架构

```
┌────────────────────────── 写入链路 (ainsert) ──────────────────────────┐
│ 长文本(.md/.txt) ─► token 滑窗切分 ─► chunk 原文入 KV / chunk 向量入向量库 │
│                          │                                            │
│                          └─► LLM 实体/关系抽取 (含 gleaning 补抽)        │
│                               ─► 去重合并 (描述 <SEP> 拼接/LLM 摘要、    │
│                                   weight 防重复累加、source_id 归并)    │
│                               ─► 知识图谱 (NetworkX) + 实体/关系向量库  │
└────────────────────────────────────────────────────────────────────────┘

┌────────────────────────── 查询链路 (aquery) ───────────────────────────┐
│ 问题 ─► LLM 提取高/低层关键词                                          │
│          ├─ local : 低层关键词 → 实体向量库 top_k → 一跳关系+关联片段   │
│          ├─ global: 高层关键词 → 关系向量库 top_k → 相连实体+关联片段   │
│          └─ naive : 问题向量   → 片段向量库 top_k                       │
│        ─► 三路 round-robin 合并去重 ─► rerank 精排 (可选, 失败自动回退) │
│        ─► token 预算截断 ─► 组装上下文 ─► LLM 生成 (SSE 流式 / 多轮历史) │
│        ─► 引用列表 (chunk → 文档标题/摘录) 随响应一并返回               │
└────────────────────────────────────────────────────────────────────────┘
```

技术栈：Python 3.11+ / FastAPI / OpenAI 兼容 LLM 与 Embedding / NetworkX / numpy / tiktoken。
部署：单容器 Docker（`docker compose up -d`）。

---

## 2. 切片策略

**按 token 滑窗切分**（`fusionrag/chunking.py: chunking_by_token_size`）：

- 窗口 1200 token、重叠 100 token、步长 1100 token（`CHUNK_TOKEN_SIZE` / `CHUNK_OVERLAP_TOKEN_SIZE` 可调）。
  相邻片段保留约 8% 的重叠内容，缓解"答案正好被切在片段边界"的信息断裂问题。
- token 计数用 tiktoken（gpt-4o-mini 词表）；离线环境自动退化为字符级可逆编码，功能不中断。
- 每个片段记录 `{tokens, content, chunk_order_index, full_doc_id}`，以 `chunk-<md5>` 为键，
  同时写入 KV 存储（原文）与向量库（检索索引），保证"检索命中 → 取回原文"一一对应。
- 选择固定滑窗而非语义切分的原因：实现对任意 Markdown/Txt 输入稳定、边界行为可预期；
  语义粒度的不足由后续阶段的**实体/关系级细粒度图谱索引**弥补——这是 GraphRAG 相对朴素 RAG 的核心增益。

## 3. 各类数据库的具体用途

全部持久化在 `WORKING_DIR` 下的 JSON 文件（原子写入），零外部服务依赖即可运行；
存储接口可替换 Redis / Milvus / Neo4j。

| 存储（文件） | 类型 | 具体用途 |
|---|---|---|
| `kv_full_docs` | JSON KV | 文档原文与生命周期状态（PROCESSING/PROCESSED/FAILED）、标题、片段/实体/关系统计；按内容哈希生成 doc_id，**重复导入幂等跳过** |
| `kv_text_chunks` | JSON KV | chunk 原文；检索命中 chunk_id 后在此取回文本 |
| `vdb_chunks` | numpy 向量库 | chunk 向量（embedding 文本 = chunk 原文）；naive 检索与 hybrid 的片段来源 |
| `kv_llm_cache` | JSON KV | 抽取/摘要/关键词/问答的 LLM 结果缓存（按模型+prompt 哈希）；重跑文档、重启服务均秒回，省钱省时 |
| `kv_entity_chunks` | JSON KV | 实体 → chunk 完整账本（不截断），是增量合并与后续"删除文档"级联清理的依据 |
| `kv_relation_chunks` | JSON KV | 关系 → chunk 完整账本，同上 |
| `graph_chunk_entity_relation` | NetworkX 图 | 知识图谱：节点=实体（entity_type / description / source_id），边=关系（weight / keywords / description / source_id）；local/global 检索的一跳扩展在此进行 |
| `vdb_entities` | numpy 向量库 | 实体向量（embedding 文本 = `实体名\n描述`）；local 检索入口 |
| `vdb_relationships` | numpy 向量库 | 关系向量（embedding 文本 = `关键词\tsrc\ntgt\n描述`）；global 检索入口 |
| `kv_chat_sessions` | JSON KV | 多轮对话历史（见下节） |

向量库检索统一用余弦相似度，阈值 `COSINE_THRESHOLD`（默认 0.2）过滤低分结果。

## 4. 长对话处理

会话管理实现于 `fusionrag/sessions.py`，策略为**持久化 + 滑动窗口**：

1. **按 session_id 持久化**：每轮问答（user + assistant 一对）追加进 `kv_chat_sessions`，
   服务重启、容器重建（volume 挂载）历史不丢；
2. **滑动窗口**：发给 LLM 的历史只保留最近 `MAX_HISTORY_MESSAGES`（默认 20）条，
   防止历史无限膨胀撑爆上下文窗口、拖慢首 token；更早的内容直接丢弃（简化策略，未做历史摘要压缩）；
3. **历史只进对话、不进检索**：检索始终针对当前问题本身，
   避免早期话题污染向量匹配，保证知识定位稳定；指代消解等上下文理解交给 LLM 在生成阶段完成；
4. **可随时重置**：`DELETE /api/v1/chat/session/{sessionId}` 清空指定会话；
5. 流式回答在 SSE 结束后才把整段答案落库，保证历史中不出现半截回复。

## 5. 可靠性设计（补充）

- **限流重试**：LLM/embedding 调用对 429/5xx/连接错误按指数退避重试（默认 5 次，`LLM_MAX_RETRIES` 可调）；
- **批量向量化**：实体/关系向量在图谱合并结束后批量写入，数十次零散 embedding 调用合并为几次；
- **精排兜底**：配置 `RERANK_MODEL` 后，合并后的检索片段先经 rerank 模型精排（低分过滤 + top_n 截断）；
  rerank 服务不可达或报错时自动回退原始排序，不阻断问答主链路；
- **答案可溯源**：响应附带引用列表（chunk → 文档标题/相关分/摘录），前端可折叠展示参考来源；
- **失败可追**：导入任一步失败，文档状态置 FAILED 并记录 error_msg，重新导入同一内容会自动重试；
- **进度可视**：导入全链路进度事件（切分/向量化/抽取 x/y/合并 x/y）经 SSE 推送，前端进度条实时展示。

## 6. 文档删除与数据一致性

删除一篇文档（`DELETE /api/v1/document/{doc_id}`，`core.py: adelete_by_doc_id`）时，
关键问题是：**实体/关系可能被多篇文档共享，不能一刀切**。FusionRAG 采用"账本裁决"思路：

1. **权威依据是实体/关系的 chunk 账本**（`kv_entity_chunks` / `kv_relation_chunks`，
   插入时维护全集），而不是图节点上可能被截断的 `source_id` 字段；
2. 对账本与本文档 chunk 有交集的每个实体/关系做**三分支裁决**：
   - `remaining = 账本chunk_ids − 本doc的chunk_ids` 为空 → **真删**：
     图节点/边、实体/关系向量（关系向量正反两个 id 都删）、账本行一并清除；
     删实体前连带清理其残留边（边不能没有端点）；
   - `remaining` 变少 → **更新**：账本与 `source_id` 重写为剩余 chunk；
     关系 `weight` 重算为 `len(remaining)`（FusionRAG 的 weight 语义即"贡献 chunk 去重计数"）；
     并**重建描述**（见下）；
   - `remaining` 不变 → **不动**；
3. **描述重建**（`DELETE_REBUILD_DESCRIPTIONS=true`，默认开）：对存活实体/关系，
   取其剩余 chunk 原文重新走一遍抽取（prompt 相同 → **LLM 缓存命中，近乎零成本**），
   用存活 chunk 的抽取记录重新合并 `description` / `entity_type` / `keywords` 并批量更新向量，
   被删文档贡献的语义碎片随之清除；个别条目重抽未命中时回退为仅重写 `source_id`/`weight`；
4. 最后删除 chunk 原文/向量与文档记录，全部存储原子落盘。

LLM 缓存不删（重导入与删除重建都依赖它）。整个删除操作幂等，
扣减是 no-op，失败后重发同一请求即可续删；与导入共用同一把锁，天然互斥。
